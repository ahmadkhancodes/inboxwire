# Inboxwire adversarial security review

12 Nov 2026. Independent pass after REVIEW.md (M5) and the m6–m9 hardening. Method: attacks run against the locally built app (`next start`, memory DB, outbox mail) with two users in two organisations, plus code reading. Every fixed finding has an exploit-style test that failed before the fix and passes now: `tests/unit/security-review.test.ts` (21 tests) and `tests/e2e/security.spec.ts` (8 Playwright tests). Not deployed.

## Threat model

**Assets**
- Customers' end users' mailboxes: OAuth refresh tokens and IMAP/SMTP passwords (sealed per org with `MASTER_KEY`), message contents fetched on demand, attachments.
- Customer secrets: API keys (hashed, prefix shown), webhook signing secrets (shown once), BYO Google/Microsoft OAuth client secrets (sealed).
- Account and org data: members, roles, invitations, audit log, delivery logs, outbox, billing state and Stripe customer, self-host licences (Ed25519, private key only in env).
- Platform: our sending domain's reputation (magic links, invites, notices), the server's network position (SSRF), plan limits (revenue).

**Actors**
- Anonymous internet user: marketing pages, sign-in, `/api/altcha`, `/api/health`, `/api/config`, hook endpoints, Stripe webhook, unsubscribe.
- End user holding a connect link (`/connect/<token>`, discover, IMAP form, OAuth start/callback).
- Signed-in customer: viewer, member, admin, owner of one org, or of several.
- API-key holder (scope read/send/admin, optionally bound to one environment).
- Founder (`ADMIN_EMAILS`) and the cron caller (`CRON_SECRET`), Prometheus (`METRICS_TOKEN`).
- Remote parties we call: mail providers, customer webhook receivers, Stripe, Google JWKS.

**Entry points**: `/api/auth/*` (Better Auth: magic link, passkey, TOTP, organization, api-key), dashboard routes `/api/*` (cookie + Origin check), `/v1/*` (API key), `/api/connect/*` (link token), `/api/hooks/gmail|graph/<envId>` (per-env token, OIDC JWT, clientState), `/api/stripe/webhook` (signature), `/api/cron/<job>`, `/metrics`, `/api/mail/unsubscribe` (HMAC token), `/api/dev/*` (404 unless `E2E_OUTBOX=1`).

## Findings, most severe first

| # | Severity | Finding | What an attacker could do | Fix |
|---|---|---|---|---|
| SR-2 | **High** | Mail flooding from our domain. `/api/auth/sign-in/magic-link` (and invitations) were limited only per IP by Better Auth (3 per 10 s). With a fresh IP per request the same address got unlimited sign-in mails (8 of 8 accepted in the probe). ALTCHA exists (`src/lib/security/altcha.ts`) but no form uses it. | Mail-bomb any inbox from our sending domain; burn the Resend quota and our domain reputation, so real sign-in links land in spam. | `src/lib/security/auth-guard.ts` runs before Better Auth on both paths: 5 mails per target address per 10 min (shared across both paths, address hashed in the limiter) and 20 per IP. The victim still gets working links, so the per-address limit cannot lock them out. |
| SR-1 | **Medium** | Open redirect through `?next=` with a control character. `safeNext` refused `//` and `\` but not tab/CR/LF; browsers strip those, so `/sign-in?next=/%09/evil.example` returned `Location: /\t/evil.example` = `https://evil.example`. Same value went to `window.location.assign` after passkey and two-factor sign-in. Better Auth's own `callbackURL` check was not affected (verified). | Send a real `inboxwire.buffersoltech.com` link that lands a signed-in customer on a look-alike page asking for their API key or a "re-login". | `safeNext` (`src/components/app/redirect.ts`) refuses control characters and anything longer than 2 KB, then resolves the path against a dummy origin and keeps it only if the origin is unchanged. |
| SR-3 | **Medium** (billing) | Free extra environments. `/api/oauth-clients` GET/PUT/DELETE called `ensureEnvironment` directly. Any member opening `?environment=staging` created the environment, and `authEnv` lets existing environments through, so a Free org got 3 environments (Growth feature) for nothing. | Use staging/development on the Free or Starter plan; no upgrade needed. | `environmentWithinPlan` (`src/lib/connect/env.ts`) is the only way to create one; `authEnv` and all three oauth-clients handlers use it (402 `environment_limit`). The OAuth-clients screen shows a plan notice with a link to Billing instead of an error. |
| SR-4 | **Medium** | Account export leaked the org audit log to members and viewers. `/api/account/export` included `exportOrgData` for every org the user belongs to, while `/api/audit` is owner/admin only. | A viewer reads every action, actor id and target id of the org (who created which key, webhook, deletion). | The export keeps each section only if the member's role may read it in the dashboard: audit log (`audit:read`), webhook endpoints (`webhook:read`), billing (`billing:read`). |
| SR-5 | **Medium** (self-host) | Unbounded request bodies. `readJson` checked `Content-Length`, then called `req.text()`, which buffers the whole stream; a chunked upload has no length. The unauthenticated Gmail/Graph hook routes used `req.json()` with no cap at all; the Stripe route `req.text()`. Vercel caps bodies at 4.5 MB, a Node server does not. | Exhaust the memory of a self-hosted instance with one slow chunked POST to `/api/hooks/graph/x`. | `readBodyText` (`src/lib/http.ts`) streams and stops at the cap (413). Used by `readJson`, the auth guard, both hook routes (256 KB) and the Stripe webhook (1 MB, raw bytes still go to the signature check). |
| SR-6 | Low | `DELETE /api/webhooks/<another org's id>` answered `200 {"deleted":true}` and wrote a `webhook.deleted` audit entry in the attacker's org. Nothing was deleted (the query is org-scoped). | An existence-agnostic but misleading answer and audit noise. | 404 unless the endpoint belongs to the caller's org. |
| SR-7 | Low (self-host) | `clientIp` took the leftmost `X-Forwarded-For` entry, which the client controls behind any appending proxy; Better Auth trusted a single client-supplied value when the app is exposed directly. | One attacker becomes many IPs for the connect-page and sign-in limits. | `clientIp` takes the rightmost hop. New `TRUSTED_PROXIES` env (Better Auth `trustedProxies`) and a self-host note: run behind a proxy that sets the header. Vercel already sends a single, platform-set value. |
| SR-8 | Low (broken control) | Admins could not create, update or revoke API keys: our role table said `apiKey: manage`, the Better Auth plugin checks `create/update/delete`, so only the owner (creator bypass) passed. | Not exploitable; the dashboard promised admins a control they did not have, which pushes teams to share the owner login. | `apiKey` statements now include the plugin's actions for owner and admin; members and viewers still only `read`. |
| SR-9 | Low | The webhook "Send test" button sent a real request per click with no limit. | Use our servers as a free request cannon against any public URL. | 10 tests per org per minute (429). No automated test: each call makes a real outbound request, which the offline CI cannot do. |

## Verified, no change needed (attempted and refused)

- **Tenant isolation**: with the attacker's session against the victim's ids: get/set-active/update/delete org, list members, invite (incl. as owner), list/get/update/delete/create API keys of the other org, PATCH/DELETE/test webhook, replay delivery: all 400/403/404. Org-scoped lists (`/api/webhooks`, deliveries, outbox, audit, live snapshot) contain none of the victim's ids. `/v1` loads accounts by `envId` (404 across env/org), API keys are environment-bound (REVIEW P1-2).
- **Roles**: member cannot change their own role, invite, create webhooks or read the audit log; admin cannot invite as owner or promote themselves; nobody can remove the only owner.
- **Auth**: magic link is single use (replay redirects with `error=INVALID_TOKEN`, no session), expires in 10 min, sign-in answers the same for known and unknown addresses (no enumeration). Session cookie `HttpOnly; SameSite=Lax`, in production `__Host-` + `Secure`. Better Auth refuses absolute, `//`, `\` and tab `callbackURL`s. Cookie requests from a foreign or missing Origin get 403 on every non-GET dashboard route; GET routes have no side effects except the HMAC-signed unsubscribe link.
- **Founder pages**: `/admin` and `/api/admin/overview` check `ADMIN_EMAILS` server-side (401/404 for others); `/metrics` 404 without `METRICS_TOKEN` in production; `/api/cron/*` 401 without `CRON_SECRET`.
- **Injection**: zod validates every JSON body (an object where a string is expected is 400, so `$ne`/`$gt` never reach Mongo); query strings are strings. E-mail templates escape every user string; CSV export neutralises `= + - @` cells; attachment downloads are `attachment` + `nosniff` with a sanitised filename; reply headers are CR/LF-stripped (REVIEW P1-5).
- **SSRF**: webhook URLs must be https, public, no credentials, no single-label hosts; checked again on every attempt with DNS; redirects are not followed; response snippet capped at 2 KB; 10 s timeout. IMAP/SMTP hosts use the same `assertPublicHost`.
- **Webhooks in**: Stripe signature on the raw body with the library's tolerance, event ids recorded after success, entitlement recomputed from Stripe, other apps' customers ignored. Gmail token + OIDC, Graph clientState per item and env match.
- **Billing**: the client picks only `plan` + `interval` from an enum; price, quota and trial come from Stripe/lookup keys. Mailbox, environment and endpoint limits are enforced server-side on every create path.
- **Secrets and exposure**: no secret values in `.next/static` (only Better Auth's env getter names), no source maps shipped, errors are `{error: code}` without stack traces, `/api/health` returns state only, `/api/config` has no per-user data, logs scrub token/secret/password/email keys.
- **Headers/CSP**: CSP, HSTS (preload), `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, COOP. Checked against the origins in use: Stripe Checkout/Portal are top-level navigations (`location.assign`), Google/Microsoft OAuth is a server redirect, analytics is same-origin `/_vercel/insights` plus the listed Vercel hosts. The whole Playwright suite (74 tests, incl. console-error watchers) passes with the CSP on.
- **Dependencies**: `npm audit --omit=dev`: 0 vulnerabilities. 8 moderate findings are dev-only (`minimatch` ReDoS via `eslint-config-next` → `typescript-eslint`); the only fix npm offers is a semver-major downgrade of `eslint-config-next`, so left as is (lint never sees untrusted input).

## Open, needs a product or ops decision

1. **ALTCHA on sign-in.** Implemented, never wired. SR-2's limits stop flooding; ALTCHA would also slow scripted sign-up of many accounts. Recommendation: add the widget to the sign-in form only if sign-up abuse shows up in the admin overview.
2. **Unlimited organisations per user.** Each new org gets a fresh Free allowance. Recommendation: cap orgs per user (e.g. 3) or make Free allowances per user; needs a pricing decision.
3. **Invitation content.** The org name and inviter name are escaped but appear in an e-mail sent from our domain, so a hostile org can phrase a phishing invite (bounded by SR-2's per-address limit and Better Auth's 100 pending invites per org). Recommendation: refuse URLs in org names.
4. **Session cookie cache.** `session_data` is trusted for up to 5 min without a DB read, so a revoked session (sign out elsewhere) keeps working for at most 5 min if the cookie was copied. Org membership is still checked live on every request. Recommendation: keep (cost) or set `cookieCache.maxAge` to 60.
5. **DNS rebinding on webhooks/IMAP** (REVIEW, still open): the address is checked, then fetched by name; pinning the checked IP needs a custom agent.
6. **`MASTER_KEY` rotation** (REVIEW P1-7, still open).
7. **Self-host without a proxy**: documented in `docs/selfhost.md` (SR-7); the app cannot tell a spoofed header from a real one without one.
